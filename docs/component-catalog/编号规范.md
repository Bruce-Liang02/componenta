# Componenta 组件形态编号规范

> 版本：v1.0
> 状态：已冻结（2026-09-13）

---

## 一、编码结构

```
<类别码><三位序号>
   │        │
   │        └─ 组内连续分配，从 001 起
   └─ 两位大写字母，对应 9 大分类
```

示例：`PT001`、`IP014`、`WF003`

---

## 二、类别码定义

| 类别码 | 类别名称       | 英文                       | 说明                             |
| ------ | -------------- | -------------------------- | -------------------------------- |
| `PT`   | 基础展示       | Presentation & Table       | 数据展示、表格、列表、描述等     |
| `IP`   | 数据录入       | Input                      | 表单、选择器、上传等             |
| `VS`   | 数据可视化     | Visualization & Statistics | 图表、统计卡片、看板等           |
| `NV`   | 导航与布局     | Navigation                 | 菜单、标签页、面包屑、布局容器   |
| `WF`   | 流程与业务编排 | Workflow                   | 流程设计器、审批、规则引擎       |
| `FB`   | 状态与反馈     | Feedback                   | 状态标签、通知、确认框、结果页   |
| `AU`   | 权限与组织     | Authorization              | 权限按钮、组织选择、登录面板     |
| `AB`   | 通用能力       | Ability / Hooks            | useRequest、useTable、请求拦截等 |
| `IG`   | 集成类         | Integration                | 文件预览、导入导出、二维码等     |

## 四、分配规则

### 规则 1：按组件分组连续编号

同一组件的全部形态编号连号，便于记忆与推断：

```
PT001–PT004  →  ProTable 高级表格（4 种形态）
PT005–PT007  →  SearchForm 查询表单（3 种形态）
PT008–PT010  →  Descriptions 详细描述（3 种形态）
```

### 规则 2：组内末尾预留空号

每组形态编号后预留 **5～10 个空号**，用于后续增补形态而不破坏连续性。

示例：ProTable 当前 4 种形态（PT001–PT004），下一组件 SearchForm 从 PT005 开始。若未来 ProTable 需新增形态，可从 PT005 前的空号中分配（如 PT004a 不存在，直接在 PT004 后插入新的 PT005，原 PT005 起顺延——但更推荐预留策略）。

**推荐预留策略**：

```
PT001–PT004  →  ProTable（当前 4 种）
PT005–PT009  →  预留（5 个空号）
PT010–PT012  →  SearchForm（当前 3 种）
PT013–PT019  →  预留（7 个空号）
```

### 规则 3：编号发布后不复用

形态下线后：

- `status` 字段标记为 `deprecated`
- 保留说明，注明替代形态
- **编号不回收**，永不分配给新形态

示例：

```yaml
- id: PT003
  status: deprecated
  deprecatedNote: '已被 PT003-v2 替代，新系统请使用 PT003-v2'
  replacedBy: PT003-v2
```

### 规则 4：版本后缀

同一形态的重大视觉/交互迭代，用 `-v` 后缀区分：

```
PT001      主版本（当前推荐）
PT001-v1   历史版本（保留对照）
PT001-v2   重大更新版
```

版本号仅在主版本发生**不兼容变更**时使用。小优化不改版本号，而是更新 `versions` 历史。

## 五、形态维度体系

每个组件从以下 5 个维度中选取 2～5 个维度做实现：

| 维度            | 编码        | 说明                 | 取值枚举                                                                               |
| --------------- | ----------- | -------------------- | -------------------------------------------------------------------------------------- |
| **D1 布局形态** | layout      | 数据/内容的排布方式  | `standard-table` / `card-list` / `compact` / `grouped` / `tree`                        |
| **D2 交互形态** | interaction | 编辑与操作的触发方式 | `inline-edit` / `modal-edit` / `drawer-edit` / `batch-edit` / `readonly`               |
| **D3 数据策略** | data        | 数据加载与渲染策略   | `frontend-page` / `backend-page` / `infinite-scroll` / `virtual-scroll` / `all-loaded` |
| **D4 视觉风格** | visual      | 视觉语言代际         | `traditional` / `modern` / `data-dense` / `card-based` / `minimal`                     |
| **D5 技术代际** | tech        | 底层技术栈选型       | `antd` / `shadcn` / `tailwind-native` / `ag-grid` / `custom`                           |

> **设计意图**：D1–D4 覆盖「行业主流」，D5 覆盖「趋势性」。同一组件至少包含 1 个传统主流形态 + 1 个现代趋势形态。

### 形态命名约定

形态名称应能体现其核心维度差异：

```
PT001 标准分页表格         → D1:standard-table + D3:backend-page + D4:traditional
PT002 卡片列表表格         → D1:card-list + D4:card-based
PT003 紧凑数据表           → D1:standard-table + D3:backend-page + D4:data-dense
PT004 虚拟滚动表格         → D1:standard-table + D3:virtual-scroll
```

## 六、废弃与替代

### 废弃流程

1. 在形态 YAML 中将 `status` 改为 `deprecated`
2. 填写 `deprecatedNote` 说明废弃原因
3. 填写 `replacedBy` 指向替代形态（若有）
4. 校验脚本不报错，但标记为 deprecated
5. 详情页显示废弃横幅，引导使用替代形态

### 替代关系表达

```yaml
- id: PT003
  status: deprecated
  deprecatedNote: '紧凑数据表在移动端体验差，已被 PT003-v2 替代'
  replacedBy: PT003-v2
```

## 八、编号申请流程

新增形态时：

1. 确定所属类别码（如 PT）
2. 确定所属组件组（如 ProTable）
3. 在组件组的预留区间内分配下一个可用编号
4. 提交 YAML 数据，运行校验脚本
5. 校验通过后合并到主分支
6. 编号即生效，不可回收
