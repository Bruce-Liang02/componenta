## 一、项目背景与目标

### 1.1 背景

在复杂 B 端业务管理系统中，前端存在大量可抽离的独立组件。实际工程中的痛点并非「缺少组件」，而是：

- **同一个组件有多种 UI 实现形态**（例如高级表格可以是标准分页表格、卡片列表、紧凑数据表、虚拟滚动表……），团队缺乏统一的选型依据；
- **选型靠口头描述**，沟通成本高，「那个带工具栏的表格」这类表述无法精准指名；
- **形态的优缺点、适用场景没有被沉淀**，导致反复踩同样的坑，或在不同模块里做出不一致的实现；
- **新人上手慢**，不知道有哪些现成形态可用，倾向于重复造轮子。

### 1.2 项目目标

建立一个 **UI 变体选型目录站（Component Variant Catalog）**，实现：

| 目标       | 说明                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------- |
| **可指名** | 每个组件的每种 UI 形态拥有唯一稳定编号（如 `PT001`），可在需求文档、评审、对话中精确引用 |
| **可选型** | 每个形态页提供优缺点、适用/不适用场景，核心是回答「**什么情况下该选哪一种**」            |
| **可浏览** | 提供一个**单页总览**，按类别铺开全部形态卡片矩阵，扫一遍即可定位候选                     |
| **可检索** | 支持按编号精确匹配、按场景关键词搜索、按技术栈/复杂度筛选                                |
| **可沉淀** | 数据集中管理，页面由数据生成，形态增减不产生返工                                         |
| **可集成** | 与 Componenta 系统打通，选型结果可直接转化为 PageSchema 配置                             |
| **可扩展** | 支持多语言、版本管理、跨组件关联等高级特性                                               |

### 1.3 非目标（明确排除）

- 本项目**不是**一个运行时组件库（不追求安装即用的 npm 包形态）；
- **不是**完整 API 文档站（API 细节非核心，选型决策信息才是核心）；
- **不承担**组件库版本管理与发布职责；
- 首版**不追求**每个形态都有可交互 demo（见[待决策事项](#九待决策事项)）。

### 1.4 与普通组件文档站的区别

| 维度     | 普通组件文档站     | 本项目                               |
| -------- | ------------------ | ------------------------------------ |
| 组织粒度 | 一组件一页         | **一组件 N 形态，每形态一页**        |
| 页面核心 | API 表格、参数说明 | **选型决策信息（优缺点/场景/对比）** |
| 编号     | 无                 | **稳定可引用的形态编号**             |
| 首页     | 组件列表           | **一页式全量形态矩阵**               |
| 使用者   | 开发者查用法       | **产品/设计/开发共同选型**           |
| 系统集成 | 独立运行           | **与 Componenta 系统联动**           |

**规模估算**：约 **60～70 个组件**，平均每个组件 **3～4 个形态**，合计约 **235 个形态**。

## 三、核心概念与术语

| 术语                       | 定义                                                                |
| -------------------------- | ------------------------------------------------------------------- |
| **类别（Category）**       | 组件的一级分类，共 9 类，对应编号前缀（PT/IP/VS/NV/WF/FB/AU/AB/IG） |
| **组件（Component）**      | 一个功能单元，如「高级表格」                                        |
| **形态（Variant）**        | 同一组件的一种具体 UI 实现效果，是**编号的最小单位**                |
| **形态编号（Variant ID）** | 形如 `PT001` 的稳定唯一标识，一经发布不改变含义                     |
| **缩略图（Thumb）**        | 形态的可视化预览，选型的第一依据                                    |
| **一句话定位（Tagline）**  | 用一行文字说清该形态是什么，全站最重要的字段                        |
| **形态组**                 | 同一组件下的全部形态，编号连续                                      |
| **跨组件关联**             | 不同组件的形态之间的搭配关系（如表格 + 筛选表单）                   |
| **形态版本**               | 同一形态的迭代版本记录，支持变更历史追溯                            |

## 四、编号体系设计

### 4.1 编码结构

```
<类别码> <三位序号>
   │         │
   │         └─ 组内连续分配，从 001 起
   └─ 两位大写字母，对应 9 大类
```

示例：`PT001`、`IP014`、`WF003`

### 4.2 各类别编号容量规划

| 类别码   | 类别             | 预估形态数 | 编号区间    | 预留        |
| -------- | ---------------- | ---------- | ----------- | ----------- |
| `PT`     | 基础展示 / 表格  | ~30        | PT001–PT030 | PT031–PT040 |
| `IP`     | 数据录入         | ~50        | IP001–IP050 | IP051–IP060 |
| `VS`     | 数据可视化       | ~30        | VS001–VS030 | VS031–VS040 |
| `NV`     | 导航与布局       | ~25        | NV001–NV025 | NV026–NV035 |
| `WF`     | 流程与业务编排   | ~20        | WF001–WF020 | WF021–WF030 |
| `FB`     | 状态与反馈       | ~20        | FB001–FB020 | FB021–FB030 |
| `AU`     | 权限与组织       | ~15        | AU001–AU015 | AU016–AU025 |
| `AB`     | 通用能力 / Hooks | ~20        | AB001–AB020 | AB021–AB030 |
| `IG`     | 集成类           | ~25        | IG001–IG025 | IG026–IG035 |
| **合计** |                  | **~235**   |             |             |

### 4.3 编号分配规则

**规则 1 — 按组件分组连续编号**

同一组件的全部形态编号连号，便于记忆与推断。

```
PT001–PT004  →  ProTable 高级表格的 4 种形态
PT005–PT007  →  SearchForm 查询表单的 3 种形态
PT008–PT010  →  Descriptions 详情描述的 3 种形态
```

**规则 2 — 组内末尾预留空号**

每组形态编号后预留 **5～10 个空号**，用于后续增补形态而不破坏连续性。

**规则 3 — 编号一旦发布不复用**

形态下线后编号标记为 `deprecated` 并保留说明，**不回收给新形态**。这是「可精确指名」的前提。

**规则 4 — 编号可扩展为小版本**

同一形态的重大视觉/交互迭代，用后缀区分，不新增编号：

```
PT001      主版本（当前推荐）
PT001-v1   历史版本（保留，供存量系统对照）
```

### 4.4 形态维度体系

每个组件从以下 5 个维度中选取 **2～5 个**维度做实现，维度组合即构成形态。

| 维度            | 说明                 | 取值示例                                               |
| --------------- | -------------------- | ------------------------------------------------------ |
| **D1 布局形态** | 数据/内容的排布方式  | 标准表格 / 卡片列表 / 紧凑密度 / 分组折叠              |
| **D2 交互形态** | 编辑与操作的触发方式 | 行内编辑 / 弹窗编辑 / 抽屉编辑 / 批量编辑              |
| **D3 数据策略** | 数据加载与渲染策略   | 前端分页 / 后端分页 / 无限滚动 / 虚拟滚动              |
| **D4 视觉风格** | 视觉语言代际         | 传统后台 / 现代简约 / 数据密集 / 卡片化                |
| **D5 技术代际** | 底层技术栈选型       | Ant Design 系 / shadcn 系 / Tailwind 原生 / AG Grid 系 |

> **设计意图**：D1–D4 覆盖「行业主流」，D5 覆盖「趋势性」。同一组件至少包含 1 个传统主流形态 + 1 个现代趋势形态。

## 五、页面设计规格

### 5.1 站点结构

```
/                → 总览目录页（单页全量矩阵）
/v/:id           → 形态详情页（一形态一页）
/demo/:id        → 形态交互演示（可选，首版仅代表形态）
/compare/:group  → 同组件形态横向对比页（阶段 5）
/guide           → 「我该选哪个」选型向导（阶段 5）
/cheatsheet      → 编号速查表（纯文本，便于复制）
```

### 5.2 形态详情页规格

**一形态一页，统一模板。**

```
┌─────────────────────────────────────────────────────┐
│ PT001 · 标准分页表格                      [复制编号] │  ← 编号 + 名称
│ 所属组件：ProTable    类别：基础展示 / 表格           │
├─────────────────────────────────────────────────────┤
│  [缩略图 16:9]   [缩略图]   [缩略图]                 │  ← 2~3 张，展示主要状态
├─────────────────────────────────────────────────────┤
│ 一句话定位：后端分页 + 工具栏 + 列设置，最通用的形态  │  ← 全站最重要字段
├─────────────────────────────────────────────────────┤
│  ✅ 优点              │  ❌ 缺点                     │
│  - ...                │  - ...                       │
├─────────────────────────────────────────────────────┤
│  🎯 适用场景          │  🚫 不适用场景               │
│  - ...                │  - ...                       │
├─────────────────────────────────────────────────────┤
│  🔀 同类形态对比：vs PT002 / PT003                   │
│  🔗 跨组件关联：常搭配 IP005（筛选表单）使用          │  ← 新增
│  🛠 技术实现参考：AntD Table + useRequest            │
│  📊 复杂度：★★☆☆☆     推荐指数：★★★★☆            │
│  ⚡ 性能：高          无障碍：良好                   │  ← 新增
├─────────────────────────────────────────────────────┤
│  📝 版本历史：v1.0 (2026-09-13) 初始版本             │  ← 新增
│  [在线演示]   [查看源码]   [复制编号]                │
│  [在 Componenta 中使用]                              │  ← 新增：集成入口
└─────────────────────────────────────────────────────┘
```

**字段清单与必填性**

| 字段                           | 必填 | 说明                              |
| ------------------------------ | ---- | --------------------------------- |
| `id` 编号                      | ✅   | 唯一，稳定                        |
| `name` 形态名称                | ✅   | 简短，可用于口头描述              |
| `tagline` 一句话定位           | ✅   | 一行说清是什么，**最重要**        |
| `thumb` 缩略图                 | ✅   | 至少 1 张，建议 2～3 张           |
| `pros` 优点                    | ✅   | 3～5 条                           |
| `cons` 缺点                    | ✅   | 3～5 条，**必须真实，不可空洞**   |
| `useCases` 适用场景            | ✅   | 3～5 条                           |
| `antiCases` 不适用场景         | ✅   | 2～4 条，**最易被省略但价值最高** |
| `related` 同类形态             | ⭕   | 同组件其他编号                    |
| `relatedComponents` 跨组件关联 | ⭕   | 新增：搭配使用的其他组件形态      |
| `tech` 技术实现参考            | ⭕   | 具体到库/方案                     |
| `complexity` 复杂度            | ⭕   | 1～5 星                           |
| `rating` 推荐指数              | ⭕   | 1～5 星                           |
| `performance` 性能指标         | ⭕   | 新增：low/medium/high             |
| `accessibility` 无障碍         | ⭕   | 新增：basic/good/excellent        |
| `demo` 演示链接                | ⭕   | 有则可交互                        |
| `versions` 版本历史            | ⭕   | 新增：版本号 + 日期 + 变更说明    |
| `status` 状态                  | ✅   | active/deprecated                 |

> **撰写原则**：宁可字段少而实，不可字段多而空。缺点和不适用场景必须写出**真实的取舍代价**，否则整个站失去选型价值。

## 六、数据层设计

### 6.1 设计原则：Data-First

**页面全部由数据生成，禁止手写 235 个页面。**

- 单一数据源：`catalog/` 下的 YAML 文件
- 构建期读取并生成静态页面（SSG），或运行时加载 JSON
- 形态增减只需改数据，不触碰页面代码

### 6.2 数据文件结构

```
catalog/
├── PT.yaml      # 基础展示
├── IP.yaml      # 数据录入
├── VS.yaml      # 数据可视化
├── NV.yaml      # 导航与布局
├── WF.yaml      # 流程与业务编排
├── FB.yaml      # 状态与反馈
├── AU.yaml      # 权限与组织
├── AB.yaml      # 通用能力 / Hooks
└── IG.yaml      # 集成类
```

### 6.3 Schema 定义

```yaml
# catalog/PT.yaml
category: PT
categoryName: 基础展示

components:
  - component: ProTable
    name: 高级表格
    description: 列表页数据展示与操作的核心组件
    variants:
      - id: PT001
        name: 标准分页表格

### 阶段 3：缩略图生产方案

**目标**：解决**最大成本项**，确定缩略图如何批量产出。

> 235 张（或多状态 470 张）缩略图是本项目最大瓶颈，必须在此阶段定型技术路线。

**三个方案对比**

| 方案                   | 做法                                      | 优点                           | 缺点                   | 成本 |
| ---------------------- | ----------------------------------------- | ------------------------------ | ---------------------- | ---- |
| **A. 静态截图**        | 手工截图                                  | 最真实                         | 无法批量更新，成本最高 | 极高 |
| **B. 代码渲染截图**    | 每形态写迷你 demo，用 Playwright 批量截图 | 真实且可重跑，改样式即更新     | 需先有 demo            | 中   |
| **C. 示意图 / 线框图** | SVG 手绘抽象示意                          | 成本低，风格统一，不受框架限制 | 不够真实，细节缺失     | 低   |

**推荐方案：B 为主 + C 兜底**

- 需要真实观感的形态 → 方案 B
- 纯概念/趋势性形态（暂无实现）→ 方案 C

**任务**

1. 确定方案并搭建截图流水线（Playwright 脚本）
2. 定义缩略图规格：`16:9`、宽度 `800px`、WebP/PNG、命名 `/{id}-{n}.png`
3. 为 3～5 个形态试产，验证流水线可用
4. 编写批量重跑脚本

**产出**

- `scripts/shot.ts`（批量截图脚本）
- `thumbs/` 首批缩略图
- 缩略图规格说明

**验收标准**

> 一条命令可批量重新生成全部缩略图。

// 从形态数据生成 PageSchema
function generatePageSchema(variant: ComponentVariant): PageSchema {
  return {
    id: `page-${variant.id.toLowerCase()}`,
    version: '0.1',
    title: variant.name,
    layout: {
      type: 'sidebar-main',
      regions: [
        {
          name: 'main',
          blocks: [
            {
              id: `block-${variant.id.toLowerCase()}`,
              componentType: getComponentType(variant),
              componentImpl: variant.tech,
              props: generateDefaultProps(variant),
            },
          ],
        },
      ],
    },
  };
}
```

- [ ] 不适用场景是否包含**具体的量化门槛**（如「字段数 <5」）？
- [ ] 是否与同组件其他形态形成**明确区分**（vs 关系）？
- [ ] 技术实现参考是否**具体到库或方案**？
- [ ] 跨组件关联是否**真实存在**（而非强行关联）？
- [ ] 版本历史是否**清晰记录**变更内容？
